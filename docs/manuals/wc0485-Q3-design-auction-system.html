Problem Essence

Design a class that manages per-item auction bids. Each (userId, itemId) pair has at most one active bid; addBid replaces an existing bid if one already exists. updateBid and removeBid are guaranteed to target existing bids. getHighestBidder returns the userId with the largest bid for a given item, breaking ties by largest userId, or -1 if no bids exist.

The challenge is supporting O(log n) updates and deletes alongside O(log n) max queries. A plain dict gives O(1) add/remove but O(n) max; a sorted structure inverts this. The accepted solutions use two synchronized structures: a hash map as the source of truth and an ordered set or lazy-deletion heap for efficient max queries.

Decision Rule / Algorithm

Precondition: userId and itemId are both in [1, 5*10^4]; up to 5*10^4 total calls across all four operations.

Core rule: For each itemId, maintain two synchronized structures:

  1. A hash map cur[itemId][userId] = amount -- ground truth for active bids, O(1) read/write.
  2. An ordered structure (sorted set or max-heap) keyed by (amount, userId) per item -- O(log n) insert, remove, and max query.

addBid: Look up whether userId already has a bid in cur. If so, remove the old (old_amt, userId) pair from the ordered structure. Then insert (new_amt, userId) and update cur. O(log n).

updateBid: Identical to addBid, except the existence check is omitted because the bid is guaranteed to exist. O(log n).

removeBid: Look up the current amount from cur, remove (amt, userId) from the ordered structure, and delete from cur. O(log n).

getHighestBidder: Return the userId of the maximum (amount, userId) entry -- that is, set.last().userId for a sorted set, or the validated heap top for a lazy-deletion heap. Return -1 if empty. O(log n) amortized.

Lazy-deletion variant (no O(log n) targeted delete required): On add/update, always push a fresh (-amount, -userId) entry to the heap without removing the old one. On remove, delete from cur only. On getHighestBidder, pop heap entries until the top matches cur. This works because each push carries the amount at push time; after a later update the dict changes but the old heap entry's amount no longer matches cur[item][user], making it detectably stale. The total stale entries ever pushed is bounded by the total number of operations (5*10^4), so amortized cost per call is O(log n). This variant is important for Python because heapq has no O(log n) remove-by-value.

Implementation Skeleton

Python 3 -- lazy-deletion heap (most widely used pattern in accepted solutions):

import heapq
from collections import defaultdict

class AuctionSystem:

    def __init__(self):
        # cur[itemId][userId] = current active bid amount (source of truth)
        self.cur = defaultdict(dict)
        # heap[itemId] = max-heap via negation: entries are (-amount, -userId)
        self.heap = defaultdict(list)

    def addBid(self, userId: int, itemId: int, bidAmount: int) -> None:
        # Overwrite existing bid; old heap entry becomes stale automatically
        self.cur[itemId][userId] = bidAmount
        heapq.heappush(self.heap[itemId], (-bidAmount, -userId))

    def updateBid(self, userId: int, itemId: int, newAmount: int) -> None:
        # Guaranteed to exist; push new entry, old becomes stale
        self.cur[itemId][userId] = newAmount
        heapq.heappush(self.heap[itemId], (-newAmount, -userId))

    def removeBid(self, userId: int, itemId: int) -> None:
        # Delete from ground-truth dict only; heap entry silently becomes stale
        del self.cur[itemId][userId]

    def getHighestBidder(self, itemId: int) -> int:
        h = self.heap[itemId]
        d = self.cur[itemId]
        while h:
            neg_amt, neg_uid = h[0]        # peek at heap top
            uid = -neg_uid
            if uid in d and d[uid] == -neg_amt:   # top is still valid?
                return uid
            heapq.heappop(h)               # discard stale entry
        return -1

Reimplementation Checklist

  • Initialize two structures per item on first use: a hash map (userId -> amount) and an ordered structure keyed by (amount, userId).
  • In addBid, check if the user already has a bid; if so, remove the old (amount, userId) pair from the ordered structure before inserting the new one. (Lazy heap: skip removal, just push new entry.)
  • In updateBid, look up the old amount from the dict, remove the old ordered-structure entry, then insert the new one and update the dict. (Lazy heap: just push new entry and update dict.)
  • In removeBid, look up the current amount, remove (amount, userId) from the ordered structure, and delete from the dict. (Lazy heap: delete from dict only -- the heap entry will be filtered on the next query.)
  • In getHighestBidder (sorted-set variant), return the max element's userId directly via set.last() / set.rbegin(). (Lazy heap: pop stale entries until top matches dict, then return its userId.)
  • Tie-breaking: ensure the sort key is (bidAmount, userId) both ascending so that the maximum key correctly resolves ties by highest userId. A comparator that sorts only by amount, or sorts userId descending, will produce wrong answers.
  • Return -1 when the ordered structure for itemId is empty, or when itemId has never been seen.
  • In statically-typed languages (Java, C++, Rust, Go), ensure the comparator is a strict total order -- no two distinct (amount, userId) pairs should compare as equal, or the TreeSet/BTreeSet/std::set will silently drop one.

Wrong But Tempting

1. Linear scan for getHighestBidder
Keep a plain dict {userId: amount} per item, scan all entries on each query to find the max. addBid/removeBid are O(1), but getHighestBidder is O(n) where n = active bidders per item. Worst case: 5e4 getHighestBidder calls, each scanning up to 5e4 entries = 5e4 * 5e4 = 2.5e9 comparisons. TLE.
2. Sorted array with bisect insert
Maintain a sorted list per item so getHighestBidder reads the last element in O(1). Python's bisect.insort finds the insertion point in O(log n) but then shifts the list, making each insert O(n). Worst case: 5e4 addBid calls, each O(n) shift = 5e4 * 5e4 = 2.5e9 element moves. TLE. The same applies to C++ vector::insert.
3. Calling heap.remove() directly in Python
Python's heapq module has no O(log n) remove-by-value. The only way to remove a specific element is to scan the list for it (O(n)) and then call heapify (O(n)). With 5e4 updateBid and removeBid calls each costing O(n) = 5e4 * 5e4 = 2.5e9 ops. TLE. The lazy-deletion pattern avoids this entirely by never removing stale entries until they naturally surface at the heap top.

Accepted Algorithm Families

Family 1 -- Ordered Set / Sorted Structure

Maintain a sorted set per item keyed by (bidAmount, userId) in ascending order. addBid/updateBid erase the old pair then insert the new one; removeBid erases the pair; getHighestBidder reads the maximum (last) element. Every operation is O(log n) with no amortization required. Used by: C++ (std::set), Java (TreeSet), Python (SortedList), Rust (BTreeSet). Languages: C++ (1), Java (5), Python (1), Rust (2). Total: 9 solutions.

void addBid(int userId, int itemId, int bidAmount) {
    auto& userMap = userBids[itemId];
    auto& bSet    = bidSets[itemId];
    auto it = userMap.find(userId);
    if (it != userMap.end())
        bSet.erase({it->second, userId});   // remove old (amount, userId)
    userMap[userId] = bidAmount;
    bSet.insert({bidAmount, userId});        // insert new (amount, userId)
}
int getHighestBidder(int itemId) {
    auto it = bidSets.find(itemId);
    if (it == bidSets.end() || it->second.empty()) return -1;
    return it->second.rbegin()->second;     // max element -> userId
}

Family 2 -- Lazy-Deletion Heap (amount-based staleness)

Maintain a max-heap per item. addBid/updateBid always push a new entry without removing the old one. removeBid only deletes from the dict. getHighestBidder pops stale heap entries (those whose stored amount no longer matches the dict) until a valid top is found. The heap may accumulate stale entries, but the total stale entries across all operations is bounded by the total call count (5*10^4), so the amortized cost per operation is O(log n). Used by: Python (heapq, 6 solutions), Go (container/heap, 3 solutions), JavaScript (custom heap, 1 solution). Total: 10 solutions.

Excerpt from: accepted__qwen3.5-cloud-t1.0__python3.py
def addBid(self, userId, itemId, bidAmount):
    self.bids[itemId][userId] = bidAmount
    heapq.heappush(self.heaps[itemId], (-bidAmount, -userId))

def updateBid(self, userId, itemId, newAmount):
    self.bids[itemId][userId] = newAmount
    heapq.heappush(self.heaps[itemId], (-newAmount, -userId))

def removeBid(self, userId, itemId):
    del self.bids[itemId][userId]          # heap entry silently becomes stale

def getHighestBidder(self, itemId):
    heap, bids = self.heaps[itemId], self.bids[itemId]
    while heap:
        neg_amount, neg_userId = heap[0]
        userId = -neg_userId
        if userId in bids and bids[userId] == -neg_amount:
            return userId
        heapq.heappop(heap)
    return -1

Family 3 -- Version-Tagged Lazy Heap (version-based staleness)

A variant of Family 2 used by one Go solution (minimax-m2.7-cloud-t0.0-golang). Each item carries a monotonically increasing version counter. On every add/update the counter is incremented; the new version is stored both in the heap entry and in a per-user version map. On getHighestBidder, a heap entry is stale if its stored version does not match the per-user version map. This is more robust than amount-based staleness and would correctly handle the edge case where a user updates back to a previously used amount (though the problem constraints do not require this). One solution; extra per-user version map increases memory slightly vs. plain Family 2.

Excerpt from: accepted__minimax-m2.7-cloud-t0.0-golang__golang.go
func (this *AuctionSystem) AddBid(userId int, itemId int, bidAmount int) {
    data := this.getOrCreateItem(itemId)
    data.userBid[userId] = bidAmount
    data.version++
    data.userVer[userId] = data.version
    heap.Push(&data.Heap, Entry{Bid: bidAmount, User: userId, Ver: data.version})
}
func (this *AuctionSystem) GetHighestBidder(itemId int) int {
    for data.Heap.Len() > 0 {
        top := data.Heap[0]
        ver, ok := data.userVer[top.User]
        if !ok || ver != top.Ver { heap.Pop(&data.Heap); continue }
        return top.User
    }
    return -1
}

Wrong Answer2 Likely a broken tie-breaking rule. The accepted code invariant is: the sort key is (bidAmount, userId) with both components ascending, so that max naturally picks the higher userId on equal amounts. A comparator that sorts only by amount would return an arbitrary userId on ties. Alternatively, sorting userId descending within the comparator inverts the tie-break. A second possible cause: failing to remove the old ordered-structure entry when a user rebids, leaving a phantom duplicate; the structure then holds two entries for the same user, possibly returning an outdated amount as the winner.
