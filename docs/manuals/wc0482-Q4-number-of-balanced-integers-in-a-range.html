Problem Essence

An integer is balanced if it has at least two digits and the sum of its digits at odd-numbered positions (1, 3, 5, …) equals the sum of digits at even-numbered positions (2, 4, 6, …), where the leftmost digit is position 1.

Given [low, high] with values up to 1015, return how many integers in the range are balanced. Single-digit numbers are never balanced regardless of their value.

The huge range (up to 1015, i.e. 16 digits) makes brute-force impossible; you need digit dynamic programming on the decimal representation, counting via f(high) − f(low − 1).

Worked Example

Input: low = 1, high = 100  →  Output: 9

Step 1 — Frame as prefix counts.
Answer = f(100) − f(0), where f(x) = count of balanced numbers in [1, x]. f(0) = 0 (no positive integers ≤ 0).
Step 2 — Count 1-digit numbers ≤ 100.
1-digit numbers (1–9) have fewer than 2 digits → none are balanced. Contribution: 0.
Step 3 — Count 2-digit balanced numbers ≤ 99.
A 2-digit number "d₁d₂" is balanced iff sum(odd positions) = sum(even positions), i.e., d₁ = d₂.
First digit d₁ ∈ {1, …, 9}; second digit d₂ must equal d₁.
Numbers: 11, 22, 33, 44, 55, 66, 77, 88, 99 → 9 numbers.
Step 4 — Count 3-digit balanced numbers ≤ 100.
Only candidate with 3 digits and value ≤ 100 is 100 itself.
100: positions → d₁=1 (pos 1, odd), d₂=0 (pos 2, even), d₃=0 (pos 3, odd).
Sum odd = 1 + 0 = 1; Sum even = 0. 1 ≠ 0 → not balanced.
Step 5 — Combine.
f(100) = 0 (1-digit) + 9 (2-digit) + 0 (3-digit tight) = 9.
Answer = 9 − 0 = 9 ✓

Decision Rule / Algorithm

Core formula: answer = f(high) − f(low − 1), where f(x) counts balanced integers in [1, x].

DP state for f(x): process the decimal digits of x left-to-right, tracking:

  • pos — current digit index (0-based into the digit string)
  • diff — running value of sum(odd-position digits placed so far) − sum(even-position digits placed so far)
  • tight — whether all digits placed so far exactly match the prefix of x (bounds the next digit)
  • ndigits — count of significant digits placed (ignoring leading zeros)

Accept iff at end of string: ndigits ≥ 2 and diff == 0.

Leading zeros: when ndigits == 0 and the next digit is 0, skip without advancing ndigits or changing diff.

Parity rule: when placing a digit at actual position ndigits + 1 (1-indexed), if that position is odd (ndigits even), add; if even (ndigits odd), subtract.

Bounding the diff range: with at most 16 digits and at most 8 odd positions each contributing ≤ 9, the maximum diff magnitude is 8 × 9 = 72. This proves that an offset array of 145 elements (diff ∈ [−72, 72]) is sufficient, making the state space O(16 × 145 × 2) ≈ 4,640 entries — tiny.

Memoization: tight states are not cached across different values of x (the digit bound differs), so always clear the cache between calls to f() or redefine the closure.

Implementation Skeleton

class Solution:
    def countBalanced(self, low: int, high: int) -> int:
        from functools import lru_cache

        def count_up_to(x: int) -> int:
            if x < 10:
                return 0          # single-digit numbers are never balanced
            s = str(x)
            n = len(s)

            @lru_cache(maxsize=None)
            def dp(pos: int, diff: int, tight: bool, ndigits: int) -> int:
                if pos == n:
                    return 1 if ndigits >= 2 and diff == 0 else 0
                limit = int(s[pos]) if tight else 9
                total = 0
                for d in range(0, limit + 1):
                    nt = tight and d == limit
                    if ndigits == 0 and d == 0:   # leading zero: skip without counting
                        total += dp(pos + 1, 0, nt, 0)
                    else:
                        # ndigits is 0-based count of significant digits placed so far
                        # next position is (ndigits+1); odd iff ndigits is even
                        sign = 1 if ndigits % 2 == 0 else -1
                        total += dp(pos + 1, diff + sign * d, nt, ndigits + 1)
                return total

            result = dp(0, 0, True, 0)
            dp.cache_clear()      # CRITICAL: tight states are bound to this x; clear before next call
            return result

        return count_up_to(high) - count_up_to(low - 1)

Reimplementation Checklist

  • Use f(high) − f(low − 1); guard against low − 1 = 0 (return 0 when x < 10).
  • Track ndigits (significant digits placed, ignoring leading zeros) and apply sign based on ndigits % 2: even → add, odd → subtract.
  • Handle leading zeros explicitly: when the first significant digit has not yet appeared (ndigits == 0), a digit of 0 is a pass-through that advances pos but not ndigits.
  • Reject at end: accept only when ndigits ≥ 2 AND diff == 0; single-digit numbers must be excluded.
  • Use an offset of at least 72 for array-based memo (max diff magnitude = 8 × 9 = 72 for a 16-digit number).
  • Clear or re-define the memoization cache between the two calls (f(high) and f(low−1)); tight states encode the specific upper bound and must not be shared.
  • Ensure integer types accommodate high = 1015: use long / i64 / int64 throughout (Python is safe by default).
  • Verify the position convention once on example 3: "1234" → odd positions (1,3): 1+3=4; even positions (2,4): 2+4=6 → not balanced → answer 0.

Wrong But Tempting

1. Brute-force iteration

Loop from low to high, check each number digit by digit. Cost: O((high − low) × 16). Worst case: high = 1015, range = 1015, giving 1015 × 16 = 1.6 × 1016 operations → hard TLE; even at 109 ops/sec this is 18 million seconds.

2. Sharing the memoization cache across both f() calls

Defining one @lru_cache dp function outside the closure and calling it for both count_up_to(high) and count_up_to(low−1) with the same cache. The tight states carry the digit string of the first call as implicit context; when reused for the second call (different upper bound), cached tight entries return answers valid only for the first x, silently producing wrong answers on the shared entries. Always scope or clear the cache.

3. Counting leading zeros as position 1

A naïve implementation that starts counting the first digit—even if it's 0—as position 1 will assign the wrong parity to all subsequent digits for numbers shorter than the string length of x. For example, if x = "1000" and you consider number 99, the leading zeros make you think position 1 is "0" (pos 0), making 9 a position-2 (even) digit. This produces wrong counts for all values with fewer digits than x. The fix is to track ndigits separately and only begin parity counting once the first non-zero digit is placed.

Accepted Algorithm Families

1 Top-Down Digit DP — Length-Separated (free + tight phases) Python

For each call to f(x): (a) iterate over lengths 2 … len(x)−1 and count all balanced numbers of that length with a free DP (state = (pos, diff), no upper-bound); then (b) run a separate tight DP for exact length len(x). The free DP is small and reusable per length.

Source: accepted__claude-sonnet-4-6__python3.py (lines 16–30)

        def count_free(l):
            @lru_cache(maxsize=None)
            def dp(pos, diff):
                if pos == l:
                    return 1 if diff == 0 else 0
                lo = 1 if pos == 0 else 0
                result = 0
                for d in range(lo, 10):
                    nd = diff + d if pos % 2 == 0 else diff - d
                    result += dp(pos + 1, nd)
                return result
            res = dp(0, 0)
            dp.cache_clear()
            return res

2 Top-Down Digit DP — Unified with started / ndigits flag Python Go Rust TypeScript

Single DFS over the digit string; a started boolean (or ndigits counter) marks when the first non-zero digit has been placed. Leading zeros increment pos but not ndigits. Handles all lengths in one sweep. Cache key includes (pos, diff, tight, ndigits/started).

Source: accepted__deepseek-v4-pro-cloud-t0.0__python3.py (lines 11–31)

            @lru_cache(maxsize=None)
            def dp(pos: int, tight: bool, started: bool, is_odd: bool, diff: int) -> int:
                if pos == n:
                    return 1 if started and diff == 0 else 0
                limit = int(s[pos]) if tight else 9
                ans = 0
                for d in range(limit + 1):
                    next_tight = tight and (d == limit)
                    if not started:
                        if d == 0:
                            ans += dp(pos+1, next_tight, False, True, diff)
                        else:
                            ans += dp(pos+1, next_tight, True, False, diff + d)
                    else:
                        nd = diff + d if is_odd else diff - d
                        ans += dp(pos+1, next_tight, True, not is_odd, nd)
                return ans

3 Bottom-Up Iterative Tabulation (tight + free arrays) Java Python

No recursion. Maintains a freeDp[pos][diff+offset] array and a tightDp[pos][diff+offset] array, propagating counts forward digit by digit. At each position, free states fan out to all digits 0–9; tight states fan out up to the limit digit (one free-state transition for each non-limit digit). Final answer is freeDp[len][offset] + tightDp[len][offset]. Fastest Java submission (46 ms for codex-agent-gpt-5.5-high-java).

4 Precomputed Length Tables + Tight DFS Hybrid Go Rust Java C++ JS

Precompute a table of "how many balanced numbers exist for each exact digit-length" using tabular DP (no tight constraint). Sum these for all lengths 2 … len(x)−1. Then run a tight DFS only for numbers of the same length as x, starting with the first non-limit digit at each prefix step. The most innovative variant (kimi Go) decomposes each length L into its odd-position count and even-position count, building two independent partial-sum tables and combining them via dot product.

    exactLen := make([]int64, maxLen+1)

    }

Key observations tied to specific files

Go: 40× runtime spread within one language. accepted__qwen3.5-cloud-t1.0-golang__golang.go runs in 38 ms because it populates a global 17×145 precomputed table in Go's init() function — the table is built once per process, so each test case only needs a tight DFS over at most 16 positions. In contrast, accepted__minimax-m2.7-cloud-t0.0-golang__golang.go (1 356 ms) and accepted__minimax-m2.7-cloud-t1.0-golang__golang.go (1 532 ms) use a map[state]int64 with a struct key, paying struct-hashing and garbage-collection overhead on every cache lookup.

Java: bottom-up tabulation dominates. accepted__codex-agent-gpt-5.5-high-java__java.java achieves 46 ms / 46.3 MB using iterative tight + free arrays with no heap allocations inside the hot loop. accepted__qwen3.5-cloud-t1.0-java__java.java (895 ms / 91.7 MB) uses a 4-parameter recursive method with a long[][][] memo — the extra dimension (tight flag as a dimension) doubles memory and the repeated primitive array index arithmetic adds overhead.

Rust: 3× runtime spread, sub-4 MB memory across all solutions. accepted__glm-5-cloud-t0.0-rust__rust.rs runs at 308 ms using a fixed-size vec for free-path DP and a small 3-dimensional array for the tight path. accepted__glm-5-cloud-t1.0-rust__rust.rs at 921 ms uses a HashMap<(usize, usize, i32, bool), i64> — the HashMap hashing overhead on tuples is significantly more expensive than array indexing in Rust, explaining the 3× slowdown with essentially the same algorithm.

Python: two memory OUTLIERS. Median Python memory across 10 accepted solutions is ≈ 160 MB. The 3× outlier threshold is 480 MB.

  • accepted__deepseek-v4-flash-cloud-t0.0__python3.py uses 486.4 MB OUTLIER — its lru_cache state includes the boolean started, integer digits count, and diff, greatly expanding the number of unique cache entries held alive during exploration of a 16-digit upper bound.
  • accepted__minimax-m2.7-cloud__python3.py uses 509.5 MB OUTLIER — identical cause: tracks (pos, diff, started, length, tight) all together in a single lru_cache that is never cleared between calls, causing both call trees to accumulate in memory simultaneously.

By contrast, accepted__deepseek-v4-pro-cloud-t1.0__python3.py (19.6 MB) avoids lru_cache entirely: it builds a suffix-DP table using nested lists, then does a digit-by-digit tight pass with no caching.

C++: anomalously high memory (342.8 MB). accepted__kimi-k2.5-cloud-t0.0-cpp__cpp.cpp allocates a vector<vector<vector<long long>>> of shape (n+1) × (n+1) × 201 on each call to solve(). For n = 16, that is 17 × 17 × 201 × 8 bytes ≈ 464 KB per call, which is small by itself — but LeetCode's C++ memory reporter measures peak RSS including heap fragmentation from multiple test cases replayed in the same process, resulting in the reported 342.8 MB. The Go and Rust solutions in the same algorithm family use 8–17 MB because they avoid the repeated heap allocation entirely.
