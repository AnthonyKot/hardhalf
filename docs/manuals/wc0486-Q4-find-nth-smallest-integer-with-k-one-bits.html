Problem Essence

Given two positive integers n and k, return the n-th smallest positive integer whose binary representation contains exactly k ones. The integers are ranked in ascending order (1-indexed), and the answer is guaranteed to be strictly less than 2^50.

The core insight is that counting integers with exactly k set bits in a given range reduces to binomial coefficients: C(b, k) is the count of b-bit numbers (more precisely, numbers fitting in b bits) with exactly k ones. This turns rank retrieval into a combinatorial decoding problem solvable bit by bit in O(50 * k) time.

Worked Example

Input: n = 4, k = 2   Expected output: 9

We want the 4th smallest positive integer with exactly 2 one-bits. Use the greedy position-scan algorithm: scan bit positions from 49 down to 0. At each position pos, compute C(pos, k) -- the count of numbers that would use a higher set bit somewhere above pos with the remaining ones placed freely below. If n > C(pos, k), place a 1 at pos.

Decision Rule / Algorithm

Core rule: Among all positive integers with exactly k set bits, the n-th smallest can be decoded bit by bit using binomial coefficients. Scan bit positions from high (pos=49) to low (pos=0). Maintain the count of ones still needed (rem). At each position: 

if C(pos, rem) < n:
    set this bit in the answer
    n -= C(pos, rem)
    rem -= 1

Precondition: answer is guaranteed strictly less than 2^50, so bit positions 49..0 suffice.

Why C(pos, rem)? If we are deciding whether to place a one-bit at position pos, then C(pos, rem) counts the number of integers with the MSB currently being considered NOT at position pos but somewhere below -- that is, integers with exactly rem ones drawn from the lower pos positions. If n exceeds that count, the n-th number must have bit pos set; otherwise it does not.

Key bound: The maximum value of C(50, k) for any k fits in a 64-bit integer (C(50, 25) ~ 1.26e14, well within 2^63-1 ~ 9.2e18), so no big-integer arithmetic is needed in compiled languages. In JavaScript, regular number handles C(49, 24) ~ 6.3e13 without precision loss since it is below 2^53.

Time complexity: O(50 * k) for the precomputed-table variant or O(50) for the linear scan variant (since we stop when rem reaches 0). Space: O(1) with on-the-fly comb, or O(50 * k) for a Pascal triangle table.

Implementation Skeleton

Python 3 -- position-scan greedy (most common family):

from math import comb

class Solution:
    def nthSmallest(self, n: int, k: int) -> int:
        ans = 0
        rem = k
        # Scan from bit 49 down; answer is guaranteed < 2^50
        for pos in range(49, -1, -1):
            if rem == 0:
                break
            # C(pos, rem): count of integers with 'rem' ones
            # that can be placed freely in positions 0..pos-1
            c = comb(pos, rem)
            if n > c:
                # The n-th number must have bit 'pos' set
                ans |= (1 << pos)
                n -= c
                rem -= 1
            # else: bit 'pos' is 0; continue scanning lower bits
        return ans

This is a cleaned-up version of the algorithm used in accepted__kimi-k2.5-cloud-t0.0-golang__golang.go, accepted__qwen3.5-cloud__python3.py, and many others. Replace comb(pos, rem) with a precomputed table for compiled languages (see C++ and Go accepted files).

Reimplementation Checklist

  • Start scanning from bit position 49 (not 50 or 63); answer < 2^50 so positions 0..49 are enough.
  • Stop the outer loop early when rem == 0 (no more ones to place).
  • Use long long / int64 for both n and the answer -- n can be up to 2^50 and binomial values can exceed 2^32.
  • Guard C(pos, rem) when pos < rem: result is 0 (impossible to place rem ones in fewer than rem positions).
  • In compiled languages, precompute a 61x61 Pascal triangle to avoid repeated division; avoids integer division rounding errors in iterative comb formulas.
  • In JavaScript, use regular number for positions up to 49; values stay below 2^53. Only switch to BigInt if the problem ever extends to 64-bit range.
  • The condition is strict: n > C(pos, rem) (not >=). If n equals C(pos, rem), the answer sits exactly at the boundary of the zero-branch, so bit pos stays 0.
  • After the loop, verify rem == 0 in debug mode -- if it is not, the answer would have more than k ones, indicating a bug in the range or loop bounds.

Wrong But Tempting

Approach 1: Linear scan (brute force popcount)

Iterate integers 1, 2, 3, ... and count each time popcount(x) == k. Return when the counter reaches n.

Why it fails: n can be up to 2^50 ~ 10^15. At best you'd scan every integer up to the answer, which is also near 2^50. That is 10^15 iterations -- approximately 10^15 / 10^9 = 10^6 seconds. Completely infeasible.

Approach 2: Enumerate all C(50, k) combinations then sort

Generate all k-element subsets of {0..49} (each subset encodes a number with those bits set), sort the resulting integers, and return the n-th.

Why it fails: C(50, 25) ~ 1.26 * 10^14 combinations -- a 14-trillion element array far exceeds memory (10^14 * 8 bytes = 800 TB). Even for k=10, C(50, 10) ~ 10^10 = 10 billion combinations, still impossible. Only works for tiny k (k <= 6 or so).

Approach 3: Next-permutation of bits (Gosper's hack)

Start from the smallest k-bit number ((1 << k) - 1) and apply the "next permutation" bit trick n-1 times to advance to the next integer with the same popcount.

Why it fails: Each call to next-permutation is O(1), but it must be called n-1 times. With n up to 2^50, that is 10^15 calls: 10^15 * 1ns = 10^6 seconds. No better than brute force. The trick is useful only when n is small (n <= 10^7 or so).

Accepted Algorithm Families

Family A -- Greedy position-scan (combinatorial rank decoding) -- ~20 files

The dominant approach. Scan bit positions from 49 (or 59) down to 0. At each position pos, compare n against C(pos, rem). If n is larger, place a one-bit there, subtract C(pos, rem) from n, and decrement rem. Two sub-variants exist: (a) a single linear scan using a precomputed or on-the-fly binomial table; (b) an inner binary search or inner linear search to find the exact bit position for each remaining one.

Family B -- Binary search on value + digit counting -- ~4 files

Binary search over the answer range [1, 2^50]. The predicate is a digit-count function count(x, k) that computes how many integers in [1, x] have exactly k one-bits (using standard digit-DP over set bits of x). Return the smallest x such that count(x, k) >= n.

Family C -- Bit-length-first greedy -- 1 file

First determine the total bit length b of the answer (smallest b where the cumulative count C(b, k) >= n). Fix the MSB at position b-1, subtract the count of all (b-1)-bit numbers with k ones from n, then fill bit positions b-2 down to 0 with the remaining greedy scan.

    b += 1
result = 1 << (b - 1)
ones_needed -= 1
n -= comb(b - 1, k)
for pos in range(b - 2, -1, -1):
    if ones_needed == 0:
        break
    count_if_zero = comb(pos, ones_needed)
    if n > count_if_zero:
        n -= count_if_zero
        result |= (1 << pos)
        ones_needed -= 1

Runtime Outliers

Python outlier -- glm-5-cloud: accepted__glm-5-cloud__python3.py runs in 399 ms vs the Python median of ~17.5 ms -- ~23x the median. This solution uses binary search over [1, 2^50] (50 iterations) with an inner digit-scan loop and a custom non-cached comb() function recalculated from scratch each call; likely the combination of three nested loops (binary search, digit scan, comb loop) and Python's interpreter overhead accounts for the extreme slowdown.

Python outlier -- kimi-k2.5-cloud: accepted__kimi-k2.5-cloud-t0.0__python3.py runs in 208 ms -- ~12x the median. It also uses binary search with a digit-count function, likely accumulating high per-iteration overhead from Python function call dispatch inside the 50-step binary search.

Python outlier -- deepseek-v4-pro-t1.0: accepted__deepseek-v4-pro-cloud-t1.0__python3.py runs in 157 ms -- ~9x the median. It uses a 65x65 Pascal triangle initialized as a 2D list inside the function body on every call; likely the O(65^2) = 4225-cell table initialization in pure Python adds significant constant overhead even though the algorithm itself is O(60).

JavaScript outlier -- glm-5-cloud: accepted__glm-5-cloud-t0.8-javascript__javascript.js runs in 86 ms vs the JavaScript median of ~29 ms -- ~3x the median; likely because it uses BigInt for all arithmetic in its binary-search-based countNumbers function, while the fast solutions (kimi at 2 ms, deepseek-pro at 22 ms) use either regular Number or limit BigInt to the final return conversion.
