Problem Essence

Implement a ride-sharing dispatcher backed by two independent FIFO queues -- one for waiting riders and one for available drivers. The matchDriverWithRider operation always pairs the earliest-added driver with the earliest-added non-canceled rider, removes both from the system, and returns [driverId, riderId]. Riders may call cancelRider at any time before being matched; a canceled rider must be skipped silently during matching rather than surfaced as an error. If either queue has no eligible member at match time, return [-1, -1].

Decision Rule / Algorithm

Core rule: maintain three structures -- a rider deque, a driver deque, and a hash set of "active" rider IDs (those added but not yet matched or canceled).

  1. addRider(id): append to rider deque AND insert into active set. O(1).
  2. addDriver(id): append to driver deque. O(1).
  3. cancelRider(id): remove id from active set only. The ID stays as a tombstone in the deque. O(1). No need to physically touch the deque.
  4. matchDriverWithRider(): drain tombstones from the rider deque front (pop any ID not in the active set). Then check if both deques are non-empty; if not, return [-1, -1]. Otherwise pop one driver and one rider, remove the rider from the active set, and return [driverId, riderId].

Complexity: Each rider ID enters the deque once and leaves once (either drained as a tombstone or popped as a successful match). Total tombstone drains across all matchDriverWithRider calls is O(n) amortized. Cancel is O(1). Space is O(n) for n riders and n drivers.

Why active set instead of physical removal? Deque internal removal is O(n) per call. For 1000 riders all canceled and then 1000 match calls the eager approach costs 1000*1000 = 1e6 comparisons; the lazy approach costs n total drain steps regardless of cancel pattern. Both are within the n=1000 constraint, but the lazy approach is the idiomatic production pattern.

Precondition on IDs: constraints guarantee each riderId and driverId is unique within its pool and added at most once. This means the active set never holds stale entries from re-insertion, and physical queue removal in the eager approach never removes the wrong element due to duplicate IDs.

Implementation Skeleton

Python 3 -- lazy-deletion approach. Uses the function signature from stats.json.

from collections import deque
from typing import List

class RideSharingSystem:

    def __init__(self):
        self.riders: deque  = deque()  # FIFO queue; may contain canceled tombstone IDs
        self.drivers: deque = deque()  # FIFO queue of available drivers
        self.active: set    = set()    # IDs of riders not yet matched or canceled

    def addRider(self, riderId: int) -> None:
        self.riders.append(riderId)
        self.active.add(riderId)

    def addDriver(self, driverId: int) -> None:
        self.drivers.append(driverId)

    def matchDriverWithRider(self) -> List[int]:
        # drain tombstones -- canceled riders sitting at the front of the queue
        while self.riders and self.riders[0] not in self.active:
            self.riders.popleft()
        # no eligible rider or no driver available
        if not self.riders or not self.drivers:
            return [-1, -1]
        driver = self.drivers.popleft()
        rider  = self.riders.popleft()
        self.active.discard(rider)    # remove matched rider from active set
        return [driver, rider]

    def cancelRider(self, riderId: int) -> None:
        # O(1): mark inactive; drain happens lazily on the next match call
        self.active.discard(riderId)

Reimplementation Checklist

  • Rider queue is FIFO -- use deque/ArrayDeque/VecDeque, not a sorted structure or priority queue.
  • Driver queue is also FIFO -- drivers are matched in arrival order, not by smallest ID.
  • Maintain a separate hash set (active set) tracking rider IDs that are still waiting.
  • cancelRider removes from the active set only; do NOT physically remove from the rider deque.
  • matchDriverWithRider drains tombstones from the rider deque front BEFORE the emptiness check.
  • After a successful match, discard the matched rider ID from the active set.
  • Return exactly [-1, -1] (not null, not an empty array) when no match is possible.
  • In Rust: all four operational methods mutate state and must take &mut self, not &self.

Wrong But Tempting

1. Matching by smallest ID (min-heap) instead of FIFO arrival order

A min-heap or sorted insert would pair the driver/rider with the smallest integer ID. The problem requires FIFO on arrival, not sorted order. Counterexample: addRider(3), addRider(1) -- heap pops 1 first, but the correct answer at the first match is rider 3 (arrived first). Example 1 from the problem statement demonstrates this: rider 3 is matched before rider 1 even though 3 > 1. This produces Wrong Answer on nearly every test case with non-monotone insertion order.

2. Physical removal from the deque inside cancelRider -- O(n) and brittle

Calling deque.remove(riderId) (Python) or Queue.remove(riderId) (Java) is O(n) per cancel. For n=1000 riders all canceled: 1000 * 1000 / 2 = ~5e5 comparisons. Within the stated constraint (1000 total calls), this is still accepted -- and several accepted files do exactly this. The danger is correctness, not performance: if the guard "rider exists and has not been matched" is omitted or implemented with a stale data structure, the remove may silently do nothing (deque no longer contains it) OR incorrectly attempt to remove an ID that was already popped. The lazy-deletion approach sidesteps this entirely.

3. Forgetting to drain tombstones before the emptiness check

A common bug: call cancelRider on several riders, then call matchDriverWithRider. If the code checks if not self.riders or not self.drivers: return [-1, -1] BEFORE draining tombstones, the rider queue is non-empty (it holds canceled IDs), so the check passes, and the code then pops a canceled rider and returns it as a valid match. Symptom: returns [driverId, canceledRiderId] instead of [-1, -1] or the next valid pair. This is the most likely root cause of the 1 Wrong Answer in the failure stats.

Accepted Algorithm Families

Family A -- Lazy Deletion with Active Hash Set

Two FIFO queues. A hash set tracks which rider IDs are currently active (added, not yet matched or canceled). cancelRider is O(1) -- remove from set only. matchDriverWithRider drains tombstones from the rider queue front in a while-loop, then pops one from each queue. Total drain work is O(n) amortized. This is the recommended pattern and covers the majority of accepted files across all languages.

Illustrative excerpt (source: accepted__kimi-k2.5-cloud-t0.0-cpp__cpp.cpp):

    queue<int> drivers;
    queue<int> riders;
    unordered_set<int> activeRiders;

    vector<int> matchDriverWithRider() {
        while (!riders.empty() &&
               activeRiders.find(riders.front()) == activeRiders.end()) {
            riders.pop();        // drain canceled tombstones from front
        }
        if (drivers.empty() || riders.empty()) return {-1, -1};
        int driverId = drivers.front(); drivers.pop();
        int riderId  = riders.front();  riders.pop();
        activeRiders.erase(riderId);
        return {driverId, riderId};
    }

    void cancelRider(int riderId) {
        activeRiders.erase(riderId);    // O(1), no deque touch
    }

Family B -- Eager Linear Removal on Cancel

Two FIFO queues (deque or plain array). cancelRider physically searches the rider queue and removes the ID in O(n). matchDriverWithRider simply pops from the front of each queue -- no tombstone drain needed because canceled entries were already removed eagerly. Correct for n <= 1000. Some variants (minimax Python) rebuild the entire rider deque as a new deque excluding the canceled rider, which is also O(n).

Representative files: accepted__glm-5-cloud__python3.py, accepted__minimax-m2.7-cloud__python3.py, accepted__kimi-k2.5-cloud-t0.0-java__java.java, accepted__glm-5-cloud-t0.8-java__java.java, accepted__deepseek-v4-flash-cloud-t0.0-javascript__javascript.js, accepted__deepseek-v4-pro-cloud-t0.0-javascript__javascript.js, accepted__glm-5-cloud-t0.8-javascript__javascript.js, accepted__kimi-k2.5-cloud-t0.0-javascript__javascript.js.

Illustrative excerpt (source: accepted__glm-5-cloud__python3.py -- full 25-line file):

from collections import deque
from typing import List

class RideSharingSystem:

    def __init__(self):
        self.riders = deque()
        self.drivers = deque()

    def addRider(self, riderId: int) -> None:
        self.riders.append(riderId)

    def addDriver(self, driverId: int) -> None:
        self.drivers.append(driverId)

    def matchDriverWithRider(self) -> List[int]:
        if self.riders and self.drivers:
            driver = self.drivers.popleft()
            rider  = self.riders.popleft()
            return [driver, rider]
        return [-1, -1]

    def cancelRider(self, riderId: int) -> None:
        if riderId in self.riders:
            self.riders.remove(riderId)   # O(n) linear scan on deque
