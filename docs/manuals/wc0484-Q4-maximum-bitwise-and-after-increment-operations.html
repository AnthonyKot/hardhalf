Problem Essence

Given an integer array nums and budgets k (total +1 increments available) and m (subset size required), choose any m elements -- after optimally spending at most k increments -- so that their bitwise AND is as large as possible.

Because AND requires every chosen element to share a bit, maximizing the AND means aligning m elements to a common high-bit pattern. Incrementing an element past a bit boundary "rounds it up" and sets that bit, but also clears lower bits as a carry side-effect -- so cost is not simply target minus current value.

The key insight is that bits can be decided greedily from the most-significant downward: once a high bit is locked in, only candidates that can also set the next lower bit (with remaining budget) are worth considering.

Worked Example

nums = [3, 1, 2], k = 8, m = 2 -> 6

Run the greedy bit-by-bit loop from bit 30 down. Bits 30 through 3 produce candidates >= 8 whose cheapest two elements already cost more than k=8 (e.g. candidate=8 needs 5+6=11 ops). We pick up the trace at bit 2:

BitCandidate (ans | 1<<b) cost(3,c)cost(1,c)cost(2,c) 2-smallest sumAccept?
24 = 100 1 (3->4)3 (1->4)2 (2->4) 1+2 = 3 <= 8YES -- ans = 4
16 = 110 3 (3->6)5 (1->6)4 (2->6) 3+4 = 7 <= 8YES -- ans = 6
07 = 111 4 (3->7)6 (1->7)5 (2->7) 4+5 = 9 > 8NO -- ans stays 6

Cost detail for cost(3, candidate=6): 3 = 011, 6 = 110. missing = 6 & ~3 = 100 (bit 2 is the highest missing bit, b=2). Clear bits 0..2, set bit 2, OR in lower bits of mask: Y = (3 & ~0b111) | 0b100 | (6 & 0b011) = 0 | 4 | 2 = 6. Cost = 6 - 3 = 3.

Final answer: ans = 6. Optimal: increment index 0 (3->6, cost 3) and index 2 (2->6, cost 4), total cost 7 <= 8. AND(6, 6) = 6.

Decision Rule / Algorithm

Greedy bit-scan from bit 30 down to bit 0. Maintain ans = 0. At each bit b:

  1. Form candidate = ans | (1 << b) (carry previously accepted bits).
  2. For every x in nums, compute cost(x, candidate).
  3. Sort costs ascending; if sum(costs[:m]) <= k, set ans = candidate.

Cost formula (O(1) per element). If (x & mask) == mask, cost = 0. Otherwise:

  1. Find b = highest bit in (mask & ~x) -- the highest bit mask requires that x lacks.
  2. Compute Y = (x with bits 0..b cleared) | (1 << b) | (mask & ((1<<b)-1)).
  3. Cost = Y - x (always >= 0 by construction).

Correctness of Y: clearing bits 0..b and then setting bit b is equivalent to rounding x up to the next multiple of 2^b (forcing the carry to produce a clean 1 at bit b). The lower bits of mask are then OR-ed in for free because those positions are now zero after the rounding. No cheaper Y exists because any smaller target with bit b set would require bits below b to be different from what mask demands.

Bit range precondition. Iterating bits 30..0 is sufficient because max(nums) <= 10^9 < 2^30 and k <= 10^9 < 2^30, so the maximum achievable element value is at most 2 * 10^9 < 2^31. Bit 30 is the highest bit that can ever appear in a cost-efficient answer. Using bit 31 with a signed 32-bit integer causes undefined behavior (signed overflow).

Complexity. 31 iterations * O(n log n) sort = O(31 n log n) total. For n = 5 * 10^4: ~31 * 5*10^4 * 16 = ~2.5*10^7 ops.

Implementation Skeleton

from typing import List

class Solution:
    def maximumAND(self, nums: List[int], k: int, m: int) -> int:
        def min_cost(x, mask):
            # Minimum +1 ops to make (x & mask) == mask
            if (x & mask) == mask:
                return 0
            missing = mask & ~x              # bits required by mask but absent in x
            b = missing.bit_length() - 1     # highest missing bit position
            low = (1 << (b + 1)) - 1         # bitmask for bits 0..b
            # Round x up past bit b, then OR in required lower bits of mask
            y = (x & ~low) | (1 << b) | (mask & (low >> 1))
            return y - x                     # guaranteed >= 0

        ans = 0
        for bit in range(30, -1, -1):        # bit 30 is enough (values < 2^31)
            candidate = ans | (1 << bit)     # keep previously accepted bits
            costs = sorted(min_cost(x, candidate) for x in nums)
            if sum(costs[:m]) <= k:          # use int64-safe sum (Python handles it)
                ans = candidate
        return ans

Reimplementation Checklist

  • Start the bit loop at 30, not 31 -- 1 << 31 is a negative signed int in Java and C++, producing an incorrect candidate.
  • Always form candidate = ans | (1 << bit), not just 1 << bit -- previously accepted bits must persist into the candidate.
  • Compute missing = mask & ~x (not mask ^ x) -- XOR would include bits x has that mask does not, giving a wrong highest-missing-bit.
  • Identify the highest missing bit with bit_length() - 1 (Python), 31 - numberOfLeadingZeros(missing) (Java), or bits.Len32(uint32(missing)) - 1 (Go).
  • After clearing bits 0..b and setting bit b, also OR in mask & ((1<<b)-1) -- the lower bits of mask -- otherwise the cost function underestimates.
  • Sort and sum the m smallest costs, not the m largest or all n costs.
  • Accumulate the sum in a 64-bit type: m up to 5*10^4 and each cost up to ~10^9 gives a max sum of ~5*10^13, which overflows a 32-bit int.
  • Return ans after the full loop, not the last candidate tested.

Wrong But Tempting

1. Brute-force subset enumeration

Try every C(n, m) subset, compute the minimum cost to align all m elements to the same bit pattern, keep the maximum AND. For n = 5*10^4 and m = 2: C(5*10^4, 2) = ~1.25*10^9 pairs. Even O(1) per pair is ~1.25*10^9 ops -- 10x over TLE. For m = 3: ~2.1*10^13 triples.

2. Binary search on the integer answer value

Binary search over [0, 2^31] with a can_achieve(T) feasibility predicate -- 31 iterations of O(n log n) = ~2.5*10^7 ops, comfortably fast. But it is incorrect because can_achieve(T) is not monotone in T. Counterexample: nums = [5], k = 0, m = 1. can_achieve(5) = True (5 already has all bits of 5), but can_achieve(3) = False (reaching 3's bit 1 from 5 requires incrementing 5 to 6, cost 1 > 0). Binary search exploring mid=3 marks False and contracts hi=2; it returns 1 instead of 5. Among the 17 accepted solutions, the two glm-5 files use this approach and happened to pass LeetCode's provided test suite -- but this does not establish correctness on all valid inputs per the given constraints.

3. Greedy: sort nums descending, increment the top m

Pick the m largest elements and spend all k increments on them, hoping the AND converges. Fails because bit alignment matters more than raw value. A small element very close to a bit boundary may converge to the optimal AND target far cheaper than a large element misaligned with that boundary. Example: nums = [7, 8], k = 1, m = 2. The "top 2" are both chosen. AND(7, 8) = 0, and one increment cannot help. But with a targeted approach, no meaningful AND is achievable anyway -- but in larger examples, alignment-aware subset selection changes the winner entirely.

Accepted Algorithm Families

Family 1 -- Greedy bit-down, direct formula cost

The dominant approach across 10 of 17 solutions. For each element, a single arithmetic expression constructs Y from the highest missing bit. O(1) per element per bit iteration. Covers: claude-sonnet-4-6 (Py), deepseek-v4-pro t0.0/t1.0 (Py), deepseek-v4-pro (Java/JS), deepseek-v4-flash (Java), codex-gpt-5.5 (Java), qwen3.5 (Go).

Source: accepted__deepseek-v4-pro-cloud-t0.0-java__java.java 

private int costToReach(int x, int target) {
    int missing = target & ~x;
    if (missing == 0) return 0;
    int highestBit = 31 - Integer.numberOfLeadingZeros(missing);
    int mask = (1 << highestBit) - 1;
    long y = ((x | mask) + 1L) | (target & mask);
    return (int)(y - x);
}

Family 2 -- Greedy bit-down, iterative bit-scan cost

Same outer greedy loop but cost is computed by iterating through the bits of mask from high to low, setting each required bit with a carry operation. O(31) per element rather than O(1), but simpler to reason about. Covers: kimi-k2.5 (Py, Java, Go, TS), minimax-m2.7 (Py, Go).

Source: accepted__kimi-k2.5-cloud-t0.0__python3.py 

def cost(x: int, mask: int) -> int:
    if (x & mask) == mask:
        return 0
    y = x
    temp = mask
    while temp:
        b = temp.bit_length() - 1
        if ((y >> b) & 1) == 0:
            y = ((y >> b) + 1) << b  # round up past bit b
        temp ^= (1 << b)             # clear processed bit
    return y - x

Family 3 -- Binary search on answer value

Wraps the same feasibility check in a binary search over [0, 2^31]. Asymptotically equivalent to the greedy approach (31 * O(n log n)), but relies on can_achieve(T) being monotone in T -- a property that does not hold in general (see "Wrong But Tempting"). Passed LeetCode's test cases. Covers: glm-5 (Py, Java).

Source: accepted__glm-5-cloud-t0.0__python3.py 

lo, hi = 0, 2**31
while lo < hi:
    mid = (lo + hi + 1) // 2
    if can_achieve(mid):
        lo = mid
    else:
        hi = mid - 1
return lo

Family 4 -- Greedy bit-down with incremental cost propagation

Maintains a per-element costs[] array from the previous accepted iteration. Elements already compatible with ans (cost = 0) get their new-bit cost recomputed from nums[i]; incompatible elements (cost > 0) simply add the new bit value to their running cost. Avoids recomputing from scratch each iteration. Covers: qwen3.5 (Java only).

for (int i = 0; i < n; i++) {

            currentCosts[i] = val - nums[i];

    } else {

}
